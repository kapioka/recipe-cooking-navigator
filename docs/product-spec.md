# 製品仕様

## 1. Goal

調理者がスマートフォンを見ながらレシピ全体を事前に把握し、手が汚れている場面でも音声で安全に調理を進め、調理後の経験を次回のレシピ改善へつなげられること。

## 2. Success criteria

Android MVPは少なくとも次を満たす。

- ホーム画面でレシピ一覧と「ChatGPTレシピを取り込む」を分かりやすく提示する
- ホーム画面で料理名、食材名、ユーザータグを部分一致検索できる
- 検索入力中に一致する料理名、食材名、タグの候補を提示できる
- 各Recipeにユーザーが最大5個のタグを付けられる
- Recipe JSONを共有またはファイルから受信できる
- Schemaに適合しないデータを無理に解釈せず拒否できる
- 同一Recipeの複数Versionをローカル保存できる
- 最新Versionと次回使用Versionを分けて管理できる
- 任意の過去Versionを次回使用版へ戻せる
- 任意VersionをベースにChatGPTへ再改善を依頼できる
- 調理開始前に材料、全体工程、器具、事前準備を確認できる
- 調理モードでは1工程ごとに材料名とその工程で使う分量を表示できる
- 火加減、時間、完了判断、次工程予告を確認できる
- 音声で主要操作を実行できる
- 現在工程を音声読み上げできる
- タイマーはユーザー操作で開始でき、終了しても自動で次工程へ進まない
- 調理モード中だけ画面常時点灯を有効化できる
- 調理後に実難易度、味の偏り、実際の変更、一言メモ、次回希望を保存できる
- 元レシピと評価をFeedback JSONとして共有できる

## 3. Primary user flow

1. ChatGPTでRecipe JSONを生成する
2. 共有またはファイル経由でRecipe Cooking Navigatorへ送る
3. アプリがSchema検証する
4. 新Recipeまたは新Versionとしてローカル保存する
5. レシピ詳細で材料と全体工程を見る
6. 事前準備をチェックする
7. 「調理開始」でCooking modeへ入る
8. 画面操作または音声操作で各工程を実行する
9. 必要に応じて現在工程を読み上げる
10. タイマーがある場合はユーザーが開始する
11. 完成後にCook SessionとEvaluationを保存する
12. 必要なら「ChatGPTで改善」からFeedback JSONを共有する
13. 修正版Recipe JSONを新Versionとして取り込む
14. 新Versionを通常は使用版にできるが、任意の過去Versionへ戻せる

## 4. ホーム画面

アプリ起動直後はレシピ一覧を主画面とする。

主要要素:

- 「ChatGPTレシピを取り込む」
- レシピ検索欄
- 保存済みレシピ一覧
- 料理名
- 使用中Version
- 最新Versionが別に存在する場合の表示
- 必要に応じて直近評価・実難易度

ユーザー向けUIでは`JSON`を主要語として使わない。内部形式を説明する必要がある設定・エラー画面を除き、「ChatGPTレシピ」「レシピを取り込む」「レシピを書き出す」等を優先する。

### レシピ検索

ホーム画面上部に検索欄を配置し、次の項目を横断して部分一致検索する。

- 表示対象Revisionの料理名
- 表示対象Revisionに含まれる食材名
- Recipe IDに紐づくユーザータグ

検索語はいずれかの項目に一致すれば、そのRecipeを検索結果へ表示する。検索語が空の場合は通常のレシピ一覧へ戻す。

入力中は一致する料理名、食材名、タグを候補として表示し、候補には種類が分かる表示を付ける。同じ候補文字列は重複表示せず、候補を選択するとその語で検索結果を絞り込む。

初期実装の照合では、前後の空白を除去し、英字の大文字・小文字と全角・半角の違いを吸収する。ひらがな・カタカナ間の自動変換や類義語検索、曖昧検索はMVP必須にしない。

検索と候補生成は端末内で完結させ、検索語やレシピ情報を外部サービスへ送信しない。

### ユーザータグ

- 1つのRecipe IDにつき最大5個まで追加できる
- タグは追加、編集、削除できる
- 空文字は保存しない
- 前後の空白と表記正規化後に同一となるタグは重複保存しない
- タグはRecipe RevisionではなくRecipe IDへ紐づけ、すべてのRevisionで共通利用する
- タグ編集だけでは新しいRecipe Revisionを作らない
- タグは端末内の整理用メタデータとし、Recipe JSONへ追加しない
- Feedback JSONやSNS共有物へ自動的に含めない

### Google Drive Recipe Inbox

次の実装単位として、Google Drive上の専用フォルダへ置かれたRecipeをアプリから手動で一括確認する受信経路を追加する。

この機能はクラウド同期やバックアップではない。Google DriveをRecipeファイルの受け渡し場所として使い、取り込んだRecipeの正本は従来どおりアプリの端末内保存とする。Google Drive API、アプリ独自のGoogleログイン、専用バックエンドは使用せず、Androidのシステムフォルダ選択を介してユーザーがフォルダを指定する。

初期構成:

- 保存先はGoogle Drive内の専用フォルダとする
- 推奨フォルダ名は`Recipe Cooking Navigator/Inbox`とする
- ユーザーがAndroidのシステムフォルダ選択で`Inbox`フォルダを選び、アプリはそのアクセス権を端末内に保持する
- 1つのRecipe JSONファイルには1つのRecipe documentだけを含める
- ファイル名をRecipeのidentityとして扱わず、JSON内のRecipe IDとrevisionを正本とする
- 初期実装は選択フォルダ直下の`.json`ファイルだけを対象とし、サブフォルダは再帰走査しない

ホーム画面には`新しいレシピを確認`ボタンを配置する。この操作をユーザーが明示的に実行したときだけInboxを走査し、自動監視、バックグラウンド同期、定期取込は行わない。フォルダが未設定またはアクセス権が失われている場合は、フォルダの再選択を案内し、既存Recipeを変更しない。

一括取込規則:

- 各ファイルを独立して読み込み、JSON parse、`schema_version`、`type`、Recipe Schemaを検証する
- Schemaに適合した新しいRecipe IDまたはRevisionだけを端末内へ追加する
- 同じRecipe ID・revisionで内容も同一なら、保存済みとしてスキップする
- 同じRecipe ID・revisionで内容が異なる場合は、既存Revisionを上書きせず、そのファイルだけを拒否する
- 壊れたJSON、必須項目欠落、未対応Schemaなどの不正ファイルは推測補完せず、そのファイルだけを拒否する
- あるファイルの拒否で他の正常ファイルの処理を中止しない。ただしフォルダ自体を読み取れない場合は一括処理を開始しない
- 完了後に、取込件数、保存済みとしてスキップした件数、拒否件数とファイルごとの結果を表示する
- Inbox内のファイルは、取込後もアプリから削除、移動、名前変更、上書きしない
- 正常に取り込んだファイルと同一内容として処理したファイルは、Drive文書ID、内容SHA-256、Recipe ID、revisionを端末内の取込記録へ保存する
- 不正ファイルは取込済みとして記録せず、修正後の再確認を可能にする

初回のデータ方向は`Work → Google Drive Inbox → アプリ`の一方向だけとする。ここでいう`Work`はRecipe JSONをInboxへ配置する上流側作業を指し、アプリからWorkやInboxへRecipeを書き戻さない。Feedback OutboxはEvaluation / Feedback機能を実装するときに別の実装単位として追加する。

初期構築ではスプレッドシートとSQLデータベースを使用しない。フォルダ接続情報と取込記録はRecipe documentから分離した端末内JSONデータとして保持する。

## 5. 調理前画面

通常表示は「読むモード」として縦スクロールで全体を確認する。「調理開始」で、現在の1工程を大きく表示する「作るモード」（Cooking mode）へ切り替える。

### 必須表示

- 料理名
- 人数
- 想定調理時間
- AIによる想定難易度 1〜5
- 材料一覧
- 全体工程
- 主な器具
- 事前準備
- 現在使用するVersion

### 条件付き表示

- 器具の使い回し
- 安全に実行できる並行作業
- 保存・弁当上の注意

### 全体工程

詳細説明ではなく、各工程を1行程度で俯瞰できることを優先する。

目的は「これから何が起きるか」を事前に理解し、器具、材料、待ち時間、並行作業を予測できるようにすること。

## 6. 事前準備

- 一項目につき一作業を基本とする
- チェック可能にする
- 火をつける前に済ませられる切る、量る、混ぜる、解凍する等を優先する
- 合わせ調味料は構成材料と分量を保持する

## 7. 調理モード

各工程は単独表示でも実行可能でなければならない。

### 電子書籍型の操作体系

操作の詳細と受け入れ条件は[cooking-mode-ui.md](cooking-mode-ui.md)を参照する。

- 左30%タップで前工程、右30%タップで次工程、中央40%タップで音声操作パネルを開く
- 左スワイプで次工程、右スワイプで前工程へ移動する
- `3 / 8工程`のように現在位置を常時表示し、工程一覧から任意工程へ移動できる
- 材料、工程一覧、読み上げ、タイマー、前へ、操作方法、次への操作デッキを常時表示する
- 音声操作のON・OFFと使える言葉は、画面右上の独立ボタンから確認・変更できる
- 長い工程は縦スクロールで全文を読める。スクロールや操作UIのボタン操作を工程送りと誤判定しない
- 現在工程を端末内に自動保存し、同じRecipe revisionの「続きから」または「最初から」を選べる
- 工程を表示したことと、調理作業を完了したことを区別する

音声操作・現在工程のTTS・ユーザー起動タイマー・調理中の画面常時点灯は、電子書籍型操作を追加してもAndroid MVP必須のままとする。

### 必須情報

- STEP番号
- 工程名
- 操作内容
- 使用する材料とその工程で使う分量
- 完了判断
- 前へ / 次へ
- 音声操作状態

### 条件付き情報

- 火加減
- 加熱時間 / 待ち時間
- タイマー
- 使用器具
- 安全な並行作業
- 次工程予告

### 表示原則

「残りを入れる」「先ほどの調味料を入れる」など、過去画面を確認しなければ分量が分からない表現を避ける。

例:

- 悪い: `合わせ調味料を加える`
- 良い: `合わせ調味料（しょうゆ大さじ1、みりん大さじ1、酒大さじ1）を加える`

## 8. 音声操作

音声操作はMVP必須とする。ハンバーグの成形など、手で端末へ触れない工程でも調理を継続できることを目的とする。

初期コマンド候補:

- 「次」: 次工程
- 「戻る」: 前工程
- 「読んで」 / 「もう一度」: 現在工程の読み上げ
- 「材料」: 材料一覧
- 「全体工程」: 全体工程
- 「調理画面」: 現在工程へ戻る
- 「タイマー開始」: 現工程のタイマー開始
- 「タイマー停止」: タイマー停止
- 「残り時間」: タイマー残時間を案内

自由会話型の音声アシスタントではなく、誤操作を減らすため限定コマンドを基本とする。

音声認識した操作は画面または短い音声でフィードバックし、誤認識に気付きやすくする。

## 9. 音声読み上げ

現在工程の情報をTTSで読み上げられるようにする。

読み上げ対象は少なくとも次を含む。

- 操作内容
- 使用材料と分量
- 火加減
- 時間
- 完了判断

読み上げ文は長くしすぎず、調理中に理解できる単位へ整形する。

## 10. タイマー

- Step表示時に自動開始しない
- ユーザーがボタンまたは音声で開始する
- 終了後も自動的に次Stepへ移動しない
- 時間と`done_when`の両方がある場合、状態判断を優先できるUIにする

## 11. 時間と完了判断

時間だけを完成条件にしない。

可能な場合、次のような状態条件も保持する。

- 色
- 香り
- 火の通り
- 水分量
- とろみ
- 食感

## 12. 器具の使い回し

洗い物削減は目的の一つだが、食品安全と調理品質を優先する。

- 同じフライパンを連続工程で使える場合は明示できる
- 生肉、生魚、生卵などに触れた器具の再利用は交差汚染を避ける
- 安全性が不明な場合は再利用を提案しない

## 13. 並行作業

待ち時間に実施できる作業を保持できるようにする。

ただし、火元の監視が必要な工程で火元から離れることを前提とする提案はしない。

## 14. 画面常時点灯

- Cooking mode中だけ有効化できる
- 調理終了またはCooking mode終了時に解除する
- 通常の端末設定を恒久的に変更しない

## 15. 調理後評価

### 総合評価

1〜5。

### 実難易度

1〜5。AI想定難易度とは別フィールドとして保存する。

目安:

- 1: ほぼ迷わない
- 2: 簡単
- 3: 普通
- 4: 忙しい / 判断が多い
- 5: かなり難しい

### 味評価

味の絶対強度ではなく、**本人の理想からどちらへずれたか**を -2〜+2 で記録する。

- -2: かなり弱い
- -1: 少し弱い
- 0: ちょうどよい
- +1: 少し強い
- +2: かなり強い

対象例: 甘味、塩味、旨味・だし感、辛味、酸味、コク、香り、食感。

### 一言メモ

長文日記やSNSコメント機能にはしない。自分の記録とChatGPTへの改善材料として使える短い自由記述を基本とする。

### その他の記録

- 実際に変更したこと
- 困ったこと
- 次回変更したいこと
- 実調理時間

## 16. Recipe Version管理

同じRecipe IDのRevisionは履歴として残し、上書きしない。

アプリ側では少なくとも次を区別する。

- latest: 最後に取り込んだ最新Version
- active: 次回通常利用するVersion

新しいVersionを取り込んだ場合は通常active候補とするが、過去Versionをいつでもactiveへ戻せる。

任意の過去VersionからChatGPTへ再調整を依頼できる。新しいRevisionは、必要に応じて`parent_revision`でどのVersionをベースに作ったかを保持する。

## 17. 外部SNS共有

アプリ内SNSはMVPにも将来必須機能にも含めない。既存SNSへ共有する素材を生成する。

共有できる候補:

- 完成写真（任意）
- 料理名
- Recipe Cooking Navigatorを利用したこと
- 総合評価
- 実難易度
- 味評価 / 好み
- 公開用一言メモ
- ユーザー入力のレシピURL（任意）

自分用一言メモを無条件でSNS文章へ含めず、共有前に投稿文をプレビュー・編集できるようにする。

## 18. レシピ書き出しとURL責任

アプリはRecipeデータをポータブルなファイルとして書き出せる方向で設計する。

ただし、アプリは次を担当しない。

- 外部サービスへの自動公開
- レシピホスティング
- 公開URL発行
- 外部保存先の公開可否判定
- URL有効性確認
- URL維持 / 永続性保証

ユーザーが共有可能な場所へ保存し、必要なら自分で取得したURLをSNS共有画面へ入力する。

## 19. Local-first / privacy

Android MVPはローカル保存を基本とする。

初期版では次を必須にしない。

- アカウント登録
- 専用バックエンド
- クラウド同期
- OpenAI APIキー

ChatGPTへ改善依頼する場合だけ、ユーザー操作によって必要データを共有する。

## 20. 将来バックアップ

専用クラウド同期より先に、全Recipe、Version履歴、Cook Session、Evaluationをバックアップファイルとして書き出し / 復元する方式を検討する。

保存先はOSのファイル選択・共有機能へ委ね、特定クラウドサービスを必須にしない。

## 21. Error handling

- 不明な`schema_version`は勝手に互換扱いしない
- 必須フィールド欠落は読み込みエラーにする
- JSONとして壊れている場合は保存しない
- 一部だけ推測してCooking modeへ入らない
- 既存保存データを壊す可能性があるimportはfail-closedする

## 22. Platform scope

当面の実装対象はAndroid。最終的にはiPhone版も検討し、データ契約・ドメインモデル・主要UXは両OSで共通化できるようにする。

iOS実装はAndroid版完成後に、Mac購入、Xcode環境、iPhone実機またはTestFlight協力者を含めて判断する。

## 23. Out of scope for Android MVP

- ユーザーアカウント
- 専用バックエンド
- リアルタイムクラウド同期
- アプリ内SNS / フォロー / コメント / ランキング
- 栄養素自動解析
- 買い物リスト
- スーパー在庫 / 価格取得
- AI API直接統合
- カメラ常時監視
- 複数料理の自動スケジューリング
- 複雑な個人嗜好推定モデル
- iOSアプリ実装
