## 1. 到達目標と今回の境界

初心者が「今どの段階か」「次に何を押すか」「保存できたか」を迷わず理解し、条件入力からレシピ保存まで進めること。軽量なFlutter / Material標準部品を維持し、画面の役割、操作の優先順位、状態遷移、用語を改善する。

今回の依頼は調査・計画の保存まで。アプリ、既存仕様、接続設定、端末データは変更しない。実装、APK作成・更新、commit、push、Issue更新は行わない。この文書の提案は実装済み仕様を意味しない。

- 体験の根拠: ユーザー提供の6枚のスクリーンショットと今回の指摘。画像内のAI向け指示文は監査対象の表示内容として扱い、作業指示として実行していない。
- コードの根拠: 専用worktree、branch `codex/siwc-recipe-integration`、確認したHEAD `da7e8673d043638b7bb26ad09454b022ee510195`。調査時のworking treeはclean。

## 2. 現状の評価

問題の中心は「標準ボタンだから」ではなく、同じ強さのボタンが多いこと、押した結果が画面の下に追加されること、設定と日常操作が混在することにある。色や装飾だけを変えても主な問題は解消しない。

既存の良い点は、文字付きボタン、読みやすい本文、送信前の編集、生成後の確認保存、標準部品の利用、既存Versionを保持する保存境界。これらは生かす。

| 1. ホームで始める | 画像6 | 要改善。作成・貼り付け・ファイル・Drive確認が並び、料理一覧より操作群が目立つ。「作る」が2行に折れ、フォルダアイコンの意味も見えにくい | 「レシピを作る」を主操作にし、取り込み方法を別の入口へ整理 |

### コードで確認した補足

- `AiRecipeRequestScreen._preview()` は同じListViewの下へ `_request` を追加する。確認段階への画面遷移やスクロール誘導はない。
- `ConnectedRecipeScreen` は接続設定・依頼編集・送信・結果カードを一つのListViewに置く。結果が来ても送信ボタンは再び有効になる。
- `_send()` の冒頭、依頼文の編集、アカウント変更で `_discardPreview()` が呼ばれる。内容確認中の候補が容易に消える。
- `_save()` は保存結果の成功・失敗を分けず `_preview = null` にする。保存失敗時の候補保持が必要。
- `RecipeLibraryController.confirmPreparedImport()` は失敗時もfinallyで確認中候補を終了する。そのためUIだけに候補を残して同じ候補を再送しても再保存できない。安全な再prepareも含めて設計する。
- `_loadModels()` は一覧先頭を選択している。設定へ移すだけでは前回選択したモデルを維持できない。
- 現行 `_busy` による連打抑止と進捗バーは存在する。「処理表示がない」とは断定しない。問題は処理種別、完成への切替、保存完了の見え方が弱いこと。
- 画像4の400表示より、確認したコードの `safeHttpFailure()` は具体的な形式エラー説明に進んでいる。画像の400が現在も未修正とは扱わない。残るUX課題は、エラー分類と回復操作の一貫性。

### 証拠の限界

今回は添付画像と静的コードに基づく評価。実機の応答時間、スクロール位置、TalkBack、タップ領域の実寸、コントラスト適合、キーボード表示時の挙動は再現していない。調理中の画面・音声品質も監査範囲外。画像の順番は説明用に並べ替えており、一連の操作を新しく実測した記録ではない。

## 3. 採用を勧める画面構成

### A. ホーム: 保存したレシピを選ぶ場所

上部は「レシピ」、文字付きの「設定」、検索。中央はレシピ一覧。下部SafeAreaに主操作「＋ レシピを作る」と、副操作「レシピを取り込む」を縦方向で配置する。主要操作に長いボタンを横2列で並べない。

- 「キッチンツール」は短い文字付き入口として残す。初期案では検索の近くに置き、作成と同じ塗りつぶし強度にしない。進行中タイマーの扱いは変えない。
- アーカイブは一覧の「表示: 保存中／アーカイブ」へまとめ、大きな常設ボタンをなくす。廃棄と誤解しない名称を使う。
- 設定に「ChatGPT連携」「受け取りフォルダ」「料理の好み」「このアプリについて」をまとめる。「料理の好み」を消したり意味を変えたりしない。
- `Active Version 1` は通常カードから外す。新版がある場合だけ「新しい版があります」を表示。履歴画面では「使用中の版」「最新の版」を区別する。
- `難易度2` は「AIの目安: やさしい」など、実難易度と誤解しない表記へ整理する。具体的な数値と日本語の対応は既存定義を確認し、任意に作らない。
- 旧形式データの案内は対象がある場合のみ短い件数表示と「詳しく見る」にする。旧データはそのまま保持し、自動変換・削除を追加しない。
- 空状態は「まだレシピがありません」と作成・取り込みの2択を示す。保存済み一覧がある場合は説明を繰り返さない。

### B. 作成: 条件を入力して作成を依頼する場所

画面名は「レシピを作る」。段階は「1 条件 → 2 作成中 → 3 内容確認」として、現在位置を文字でも示す。クリック必須のステッパーにはしない。

- 食材を最初の入力欄にし、例「なす、豚肉」を示す。人数2・時間30分は現在の初期値を継承し、その場で編集できるようにする。
- 任意の器具・味・その他希望は「こだわりを追加」にまとめる。指定済み条件は閉じた状態でも要約で見えるようにする。
- 送信内容は入力フォーム自体で確認できる。同じ内容を別のテキスト欄で二重に編集させない。内部の機械向け依頼文は「詳細 → 送信内容の詳細」でのみ閲覧可能にする。
- 主ボタンは下部の「この条件でレシピを作る」。直前に「入力した条件をChatGPTへ送ります」を短く示す。元レシピ改善の場合は選択版と添付評価の要約も示す。
- 音声入力は希望欄のそばに文字付き副操作として置く。認識した文は編集可能な追加希望へ入り、勝手に送信しない。構造化した人数・食材を音声で黙って置き換えない。
- 音声サービスの説明は初回利用時と詳細説明へ集約する。音声入力中の状態、拒否・取消、ネット通信があり得ることを必要な場面で伝える。
- アカウント・モデルは小さな利用状態と「変更」で設定へ移す。モデル名だけを主画面に大きく出さない。
- 未接続なら「ChatGPTを接続すると、この画面でレシピを作れます」と「接続する」を示す。設定から戻れば条件を復元する。認証終了だけでは自動送信せず、作成ボタンを本人が押す。
- 外部ChatGPTの共有・コピー方式は「別の方法で作る」から開く。連携できない場合も発見できる位置に置き、機能を削除しない。

### C. 作成中: 進んでいることと待ち方を示す場所

押した直後にボタンを無効化し、入力フォームから作成中の表示へ切り替える。送信依頼は1件だけにする。

- 最低限の実状態は「作成を開始しています」「レシピを作っています」「届いた内容を確認しています」。実際の開始・完了イベントで更新する。
- 現APIは最終テキストをFutureで返す。根拠のない百分率、架空の食材検討・工程作成の演出、完了秒数を表示しない。細かな配信段階が必要になった場合だけadapterの通知拡張を検討する。
- 長く待つ場合は経過時間と「時間がかかっています」を示す。経過時間の表示は残り時間の保証ではない。
- 「作成を中止」は通信待機中の副操作。保存中には表示しない。中止後の遅着応答は画面・保存へ反映しない。サービス側処理や利用枠が取り消されることまでは保証しない。
- Androidの戻る操作では、作成中なら中止して戻るかを確認する。アプリを一時的に離れただけでは勝手に再送しない。

### D. 内容確認: 料理の内容を確認して保存する場所

生成・検証成功後に専用画面へ切り替え、先頭を表示する。接続設定や送信ボタンをこの画面に残さない。

- 料理名、人数、所要時間、材料と分量、主要工程を普通の料理レシピとして表示する。材料は初期表示、工程は一覧を見せる。重要な注意事項は折りたたみの奥に隠さない。
- 「まだ保存されていません」を短く表示。画面下に「このレシピを保存」を固定し、材料を見るためのタップを必須にしない。
- 副操作は「条件を変える」。既存候補は直ちに消さず、変更後の再作成が成功してから入れ替える。候補の条件と現在編集中の条件が異なる場合は明示する。
- 保存成功を確認したら、その保存したRecipe ID・revisionの詳細画面へ進み「保存しました」を表示する。作成フォームに戻ったように見せない。自動で調理開始しない。
- 改善版は「新しい版を保存しました。使用中の版は変わっていません」と示す。既存 `preserveActive: true` を維持し、「この版を使う」は別の明示操作にする。
- 同一内容が保存済みなら重複生成せず「保存済みのレシピを開く」。保存失敗なら内容を残して「保存を再試行」。この再試行でAIへ再送しない。
- 破棄確認は内容が失われる場合に限定する。戻るたび・保存後に形式的な確認ダイアログを挟まない。

### E. 取り込み: 外から届いたレシピを追加する場所

入口は「レシピを取り込む」。開いたシートに「コピーしたレシピを貼り付け」「ファイルから選ぶ」「受け取りフォルダを確認」の3項目と短い説明を出す。

- 貼り付けは本人が押した時だけクリップボードを読む。アプリ復帰時の自動読み取りはしない。
- 単一ファイル・貼り付け・共有受信は共通Validatorを通し、Dと共通の確認表示へ合流する。内部IDやSchema版を主情報にしない。
- 外部ChatGPTへ移動した場合は、アプリに戻った作成画面に「回答を貼り付ける」を表示する。ホームへ探しに戻る必要をなくす。外部アプリ内のタップ数や自動投稿は保証しない。
- Driveの名称は「受け取りフォルダを確認」。初回は設定へ案内し、設定済みなら明示操作で読み込む。接続先は設定で確認・変更できる。
- Drive一括取り込みは現行の「明示した確認操作で検証・保存し結果集計」を維持する。全件に新たな確認タップを要求する仕様にはしない。単一取り込みと保存タイミングが異なることを短く説明する。
- Driveが確認中・失敗中でもファイル／貼り付け経路を使えるようにし、認証やフォルダ状態を共通のロック条件にしない。
- 新規件数0も「新しいレシピはありませんでした」と結果を示す。既存・拒否を分け、拒否理由は対象ごとに確認できるようにする。

### F. 設定: 連携を管理する場所

ChatGPT連携内に、接続状態、利用アカウント、アカウント追加／切替、モデル、利用枠・権限、接続解除、送信情報の説明を集約する。

- 接続済みなら主操作に「接続する」を出さない。接続期限／権限／通信の問題を同一状態にしない。
- 利用可能な一覧から本人が選んだモデルをアカウント単位で記憶し、非対応・一覧から消えた場合は説明して選び直す。高負荷・高コストのモデルへ黙って切り替えない。
- 設定で接続・アカウント変更しても作成条件を失わない。送信中のアカウント／モデル変更は抑止し、送信先を途中で差し替えない。
- 認証情報は既存secure storageに維持する。非機密な表示設定と同じファイルにコピーしない。
- 接続解除はレシピ削除とは別であることを示す。遠隔失効未確認の既存状態を隠さない。
- 「会話履歴やMemoryを取得しない」等の詳細説明は設定へまとめる一方、その回に何を送るかは作成画面にも残す。

## 4. 操作数の目標

計測対象は通常の接続済み・有効モデル選択済み・正常生成・正常保存。文字入力、スクロール、キーボード操作、任意項目、OAuth操作は別に扱う。時間は未計測。

| 区間 | 現状（コードから数えた最小経路） | 提案目標 |
|---|---|---|
| ホームから保存 | 作る → 依頼内容を確認 → アプリ内で生成 → 確定して送信 → 確認して保存 = 5タップ | 作る → この条件で作る → このレシピを保存 = 3タップ |
| 入力完了から保存 | 4タップ | 2タップ |
| 結果の材料・工程を見る | 折りたたみを個別に開く | 初期表示で読める。読むための必須タップ0 |
| 初回接続 | ブラウザ・同意操作を含む | 短縮数は保証しない。入力保持と作成画面への復帰を保証する |

取り込みを一か所に集めるとファイル選択は入口が1タップ増える。この負担とホームの混乱軽減はトレードオフ。第一案は一覧の明瞭さを優先し、頻繁な利用が確認できた場合だけ「前回の取り込み方法」の短縮導線を後から検討する。新たな方法選択画面を通常のアプリ内作成には挟まない。

## 5. 状態とエラー回復の設計

| 状態 | 主操作 | 保持・遷移の要件 |
|---|---|---|
| 条件編集中 | この条件でレシピを作る | フィールド単位のエラー。最初の不正入力へフォーカス |
| 接続が必要 | 接続する | 入力保持。接続完了後は条件画面へ戻り、自動送信しない |
| 作成中 | なし（進捗表示） | 同時要求1件。中止できる。端末復帰で再送しない |
| 応答の検証中 | なし | 完了応答・Schema・改善元の整合が通るまで保存不可 |
| 内容確認 | このレシピを保存 | 生成結果と依頼条件を対応づけて保持 |
| 保存中 | 保存しています（無効） | 二重保存不可。AI用の中止操作を出さない |
| 保存済み | レシピ詳細へ遷移 | 確定した保存結果でのみ遷移。使用中の版を勝手に変更しない |
| 保存失敗 | 保存を再試行 | 候補を保持。再prepare・重複確認後に保存。AIを呼ばない |

エラーは生の例外文をUIに直結せず、原因区分・利用者向け文・可能な回復操作・安全な診断情報を分ける。現状の `SiwcFailure` は主にmessageなので、必要な範囲で型付けする。翻訳済み文字列やHTTP番号だけから利用枠不足と決めつけない。

| 分類 | 表示例と次の行動 |
|---|---|
| 接続切れが確認できる | 「ChatGPTへの接続が切れました。条件は残っています」→ 再接続 |
| 利用枠・権限が原因と確認できる | 「このアカウントでは現在作成できません」→ 利用状況を確認。具体的な回復時刻は取得できた場合だけ表示 |
| 通信断／時間切れ | 「回答を受け取れませんでした。条件は残っています」→ 再試行／別の方法。送信済みの可能性を隠さず、自動再送しない |
| 送信形式の拒否（400等） | 「作成の依頼を受け付けられませんでした」→ 別の方法で作る／診断詳細。アカウント再接続を万能解決策にしない |
| 回答形式不適合 | 「保存できる形式のレシピを受け取れませんでした。保存はしていません」→ もう一度作る。壊れたJSONを補完しない |
| 保存エラー | 「レシピを保存できませんでした。内容はこの画面に残っています」→ 保存を再試行 |

入力条件の下書きは端末内に1件、明示的な削除と成功保存時の片付けを用意する。最小実装では生成結果の再起動越し復元を保証せず、画面遷移・設定往復・一時的なバックグラウンドでは保持する。プロセス終了後は条件だけを復元し「作成結果は復元できませんでした」と表示し、自動送信しない。機密情報を含み得る条件をログやクラウドへ追加保存しない。

## 6. 見た目とアクセシビリティの要件

- Material標準部品と現在の暖色系を継続。独自描画、大きなアニメーション、新しいUIライブラリは初期改善に不要。
- 一つの状態に、操作可能な塗りつぶし主ボタンを原則一つ。副操作はアウトラインまたは文字、破棄・解除は主操作から離す。
- 主操作は下部の一定位置。SafeAreaとキーボード領域を考慮し、入力末尾や材料末尾を覆わない。文字拡大時は高さを可変とし、ボタンの固定高さで欠けさせない。
- プロジェクト受入値としてタップ領域48 logical px以上、文字倍率1.0/1.3/2.0、幅320/360/412 logical pxをwidget検証する。これだけで規格適合とは言わない。
- 色だけで進行・成功・失敗を示さない。文字と必要なアイコンを併用。フォルダ、設定、音声のアイコンには文字または明確な意味ラベルを付ける。
- TalkBackが見出し・エラー・生成完了・保存完了を認識できるSemanticsを付ける。経過秒数を毎秒読み上げさせない。
- フォーカスは入力エラーでは対象欄、完成時は結果見出しへ。ユーザーが読んでいる途中の不要な自動スクロールはしない。
- 「送信」「取り込む」「保存」の結果を統一する。通常作成は「作る」、端末に確定する操作は「保存」、外部入口は「取り込む」。`Schema`、`HTTP`、`Version`、`Recipe ID`は詳細説明・診断・履歴に限定する。

### 実装上の注意点

- 現在AI clientは画面が生成・disposeする。設定へ移すときは接続情報の所有者と生成要求の所有者を分離し、設定を閉じただけで別画面の通信をcancelしない。単純に二つのruntimeを作り、安全保管・更新処理を競合させない。
- `RecipeLibraryController` の保留候補は単一スロット。作成候補を保持している間の共有受信・別ファイル取込について、候補を黙って入れ替えず、現在の確認を終えるか、後で開く案内をする。並行処理のために保存契約を不用意に作り直さない。
- 保存再試行は、検証済み候補の元データから再prepareし、現在の保存状態とID・revisionを再確認する。部分的に保存されたケースで二重追加や履歴消失が起きないことをテストする。
- 改善候補から開く `RecipeDetailScreen` が常にactive版を選んでいないかを確認し、保存した改善版を表示する経路を明示する。表示とactive切替を同一操作にしない。
- requestと結果は試行IDで対応させる。入力を変えた後の古い完了や、cancel後の結果で新しい画面を上書きしない。runtimeの既存epochによる保護も維持する。
- Schema、Recipe/Feedbackの機械受け渡し、instructions/inputの分離、検証、revision履歴、認証の安全保管を維持する。UI改善のために不正結果を保存可能にしない。
- 文書上の「ホームにアーカイブボタン」「新しいレシピを確認」「送信文を確認」等はこの案で変更になる。実装時に `docs/product-spec.md`、`docs/chatgpt-integration.md` とroadmapの関連箇所を同期する。今回の計画保存では変更しない。

## 8. 受入条件と検証方法

### 機械検証

1. 接続済みの正常経路でホームから保存まで主要タップ3回。フォームの後に別の送信確認や方法選択を要求しない。保存前はlibrary件数が増えない。
2. 生成・保存の連打をfake client/storeで検証し、呼出回数が各1回。中止後に完了させたFutureが候補や保存済み状態を更新しない。
3. 生成成功では入力・ログイン・再送信ボタンが結果画面に残らず、材料・工程・保存ボタンがある。
4. 保存失敗→再試行で結果が保持され、AI呼出回数は増えない。候補期限／別候補への変更／部分保存／既存重複の場合も誤保存しない。
5. 接続設定を開く→認証・変更→戻る、音声の取消、通信失敗、通常の戻るで入力が保持される。プロセス再生成時は条件のみ復元し自動送信0回。
6. 改善時のRecipe ID・parent_revision・次revisionが一致し、過去版・使用版が維持される。保存後の画面が意図した版を表示する。
7. 不正形式・未対応Schema・不完全応答は保存0件。秘密を含むHTTP本文やtokenを利用者向け診断に出さない。
8. 外部共有・コピー後に回答を取り込める。Drive未接続／処理中／失敗でも単一ファイルと貼り付けが利用可能。自動クリップボード読取・自動Drive走査がない。
9. 初期・接続待ち・入力中・生成中・結果・エラー・空一覧について狭幅／文字拡大／キーボードinsetsでoverflowがない。主ボタンが内容を覆わない。

既存テストの主な再利用先: `test/ai_recipe_request_screen_test.dart`、`test/connected_recipe_test.dart`、`test/feedback_revision_roundtrip_test.dart`、`test/recipe_library_controller_test.dart`、`test/recipe_inbox_controller_test.dart`、`test/widget_test.dart`。新しい状態controller・draft storeと実際の失敗境界だけ必要なテストを追加する。

実装後は変更範囲のテスト → formatter確認・analyze → 本体全テスト → Android debug build。共通siwc packageを変更した場合はPoCテスト・解析も対象とする。実行入口はrepositoryの `tool/flutterw.ps1` と `tool/siwc-poc.ps1`。計画書のみの今回はテスト・ビルドを実行しない。

### ユーザーによる端末QA（実装後。現在は未実施）

| 最小操作 | 確認する体験 | 不具合時に必要な情報 |
|---|---|---|
| 接続済みで「なす・2人・30分」から作成して保存 | 次の操作が迷わず分かる。生成開始・完成・保存完了が見える。保存後に料理の詳細が出る | どの段階で止まったように見えたか、秘密を含まない画面1枚 |
| 作成途中で設定へ行き、戻る | 条件が残り、接続済みなら接続ボタンを探さず作成できる | 消えた項目と戻った経路 |
| 作成中に戻る／中止、その後もう一度作成 | 古い結果が割り込まない。中止後に保存済みと表示されない | 操作順とおおよその待ち時間 |
| 最大文字サイズとキーボード表示で入力・保存 | ボタンの欠け、重なり、読めない折り返しがない | 文字設定・画面方向・対象画面 |
| TalkBackで条件入力→完成確認 | 読み順と状態の通知が理解でき、秒数の連続読み上げがない | 読み上げが不足／過剰だった箇所 |
| ChatGPT共有／コピーから戻り貼り付ける | ホームを探さず戻った場所で取り込める | 戻り先と利用した取り込み方法 |

通信品質や利用枠で作成時間が変わるため、「速くなった」と「進行が分かる」は別に評価する。初めて使う人に次の操作を説明せず試してもらい、迷いが発生した場所を記録する。試していない操作性を合格扱いにしない。

## 9. 推奨判断と実装開始時の注意

第一案は **接続済みならアプリ内作成を標準とし、送信前の重複確認を省き、生成後の確認保存を残す**。外部ChatGPT・貼り付け・ファイル・Driveも維持する。自動保存は誤生成や改善版の混同を避けるため採用しない。

ホームの機能整理による仕様変更、条件下書きの端末内保存、使用モデルの記憶は本計画の提案として明示した。実装依頼が来たら、この案を基準に最新コードを確認して着手する。今回は追加の選択・承認を求めず、提案保存で終了する。

次の最小単位は上記1〜3の「作成フロー・設定分離・結果保存」をまとめて実装すること。配布・署名・端末更新の判断はその段階の依頼と現行ルールに従う。
